# FaultNet: two-person demonstration

Target: 15–18 minutes for the full rubric-aligned presentation, followed by questions. For a shorter slot, show rehearsed bandwidth/interruption records and retain the what-if evaluation and all four components. A owns application operation; B owns packet/routing explanations and Packet Tracer operation. Speak only the quoted lines. Actions are stage directions. Replace bracketed values with observations from the screen; predictions are not results. The [main demo script](demo-script.md) now maps the 30-mark rubric and includes exact what-if/report/individual-assessment checks; follow those additions as well as these speaking handoffs.

The story: **establish normal behavior, introduce a controlled fault, inspect its effect, remove it, verify recovery.** Application fault injection and Packet Tracer routing are separate experiments answering related resilience questions.

## 1. Opening — A and B, 1 minute

**A — show workbench:**

> Good morning. Our project is FaultNet, a controlled network-resilience testing lab. An application can work normally and still fail when requests become slow, bandwidth is restricted or a connection breaks. Our problem is to reproduce those conditions in a controlled way and measure their effect, rather than judge reliability from a successful normal request.

**B:**

> We examine this at two levels. FaultNet introduces software faults into real HTTP connections and records application behavior. Packet Tracer demonstrates routing and reachability when a simulated router link fails. Wireshark lets us inspect the actual traffic generated by the application tests.

## 2. Explain the four parts — A and B, 1 minute

**A — point to workbench/cockpit links:**

> The experiment workbench runs repeatable baseline, faulty and recovery phases against a fixed demo server. The live proxy cockpit is for manual testing: we configure a development target, apply faults and inspect individual requests as they finish.

**B:**

> Packet Tracer supplies the routing simulation; Wireshark supplies the packet-level observation. They have different purposes. Packet Tracer is not connected to the dashboard, and its virtual packets are not what this Wireshark capture contains.

**A — explain request path:**

> In the workbench, a test client sends real HTTP requests through our proxy to a local demo server. The demo returns the same 64 KiB payload each time. This keeps the amount of data consistent. Control traffic uses port 3000, the experiment proxy uses 3002, and the demo server uses 3001. The separate live proxy uses 8080.

## 4. Wireshark — B explains, A operates, 2 minutes

Before the delay run, on laptop A open Capture → Options, select Adapter for loopback traffic capture, and enter this in the bottom **Capture filter for selected interfaces** field:

```text
host 127.0.0.1 and (tcp port 3001 or tcp port 3002)
```

Start before the run, stop after completion and save locally. This filter excludes control port 3000 and live-proxy port 8080. [Official capture-filter instructions](https://www.wireshark.org/docs/wsug_html_chunked/ChCapCaptureFilterSection.html).

**B — show saved fresh delay capture:**

> Wireshark is our packet-observation tool. Because the client, proxy and server run on this laptop, we capture loopback traffic. Port 3002 shows the client-to-proxy connection; port 3001 shows proxy-to-server traffic. The capture is from the delay experiment we just ran.

A enters the **display filter** `tcp.port == 3002`. If HTTP is not recognized, use Analyze → Decode As → HTTP for TCP port 3002. Select a request, then Analyze → Follow → TCP Stream. [Official Follow Stream instructions](https://www.wireshark.org/docs/wsug_html_chunked/ChAdvFollowStreamSection.html).

**B:**

> This stream contains GET /payload, the HTTP response and the synthetic payload. It demonstrates that real traffic was exchanged. To inspect the injected delay, we also need packet timestamps; stream contents alone do not establish timing.

Close the stream dialog. Use the run's faulty observations' Started (UTC) values from Exact probe measurements or exported JSON to identify a faulty request. Use View → Time Display Format → UTC Date and Time of Day when matching UTC timestamps. In a capture containing only this single three-probe comparison, its fourth port-3002 GET is the first faulty request; verify against the record rather than guessing in a mixed capture. Isolate that stream and compare its GET time with the first server HTTP response time. [Official timestamp-format guidance](https://www.wireshark.org/docs/wsug_html_chunked/ChWorkTimeFormatsSection.html).

**B — only after reading the actual timestamps:**

> For this faulty request, the request-to-response gap is approximately [measured gap]. That supports the application's delay measurement. The dashboard measures complete HTTP exchange time. TCP acknowledgement round-trip time is a different measurement and should not be called the injected delay.

Do not label a FIN as a reset, invent retransmissions, or call HTTP failures proof of IP packet loss. For a prior backup capture, replace “just ran” with its actual date/settings. Optional bandwidth capture shows body delivery spread over time; optional interruption capture shows an incomplete HTTP exchange and the actual closure flags.

Click Send sample and read the actual status, bytes and elapsed time. Wait for each sample to finish before changing the configuration.

**A:**

> The workbench automates a fixed experiment. The live cockpit gives us manual control over a forwarding proxy. It can target a development application, including separate frontend and backend origins, and it monitors individual requests rather than automatically running three phases.

> This normal sample shows [actual status], [bytes] bytes and [time] milliseconds. Next I set Response delay to 500 milliseconds and click Apply changes. An edit is only a draft until Apply activates it for subsequent requests.

A sets Response delay = 500 ms, Apply changes, then Send sample. Point at sample result, altered count and finished-request details.

**A:**

> This request is marked as altered, with [actual elapsed time] milliseconds. Request delay and response delay act at different points; jitter varies the delay, and upload/download limits pace body delivery. The network presets are illustrative profiles, not measurements of a real mobile carrier.

**A:**

> Now the proxy deliberately returns HTTP 503 for this path. The client receives a valid HTTP response reporting an application error. That is different from a TCP connection failing. Probability 100 makes this rule deterministic for the demonstration.

A resets faults, sends a final sample, and reads its observed normal result.

**A:**

> Reset removes live faults and cancels active live requests while retaining applied targets. The restored sample shows [actual outcome]. Other controls allow connection stalls/disconnects, response-header changes and local JSON mocks for testing client behavior. The monitor keeps the latest 50 finished requests in memory; it is not a persistent experiment archive. The workbench's records remain saved separately.

Do not demonstrate the 60-second timeout mode in this short pitch: Send sample has its own five-second timeout. Do not claim a header or mock effect you have not shown. No live mutation changes workbench fault settings, and workbench faults do not change the live listener.

## 6. Packet Tracer — B operates and explains, 3–4 minutes

**B — show topology:**

> We now move from real local HTTP tests to a simulated routed network. Our topology has three routers in a triangle, three switches and six PCs across three LANs. The third router supplies an alternate path. We compare static routing, RIPv2 and OSPF on the same topology, failing the same direct R1–R2 link each time.

The tested pair is PC1 `192.168.0.2` to PC3 `192.168.1.2`. On PC1 → Desktop → Command Prompt:

```text
ping 192.168.1.2
```

For each project, allow interfaces/routes to settle, show healthy replies, then on R1 → Config → GigabitEthernet0/0 turn Port Status off. Do not disable the LAN interface or delete the cable. Repeat ping. Show actual replies/failures and retain transient failures. Restore the same interface before leaving each project and confirm ping; do not overwrite originals with faulted state.

**Static — B:**

> This static configuration deliberately has no backup route to PC3's LAN. After disabling the direct link, the ping shows [observed outcome]. An alternate cable alone does not provide resilience; routing must select a usable path. Static routing can have backup routes, but this control case does not configure one.

**RIPv2 — B:**

> RIPv2 exchanges routing information and selects routes using hop count. After the direct link fails and the protocol converges, this project can use R3. The ping shows [observed outcome]. We will verify the route as well as connectivity.

On R1 CLI, enter `enable` then `show ip route`. Locate destination `192.168.1.0/24`; `R` identifies RIP. In the previously verified fault case the next hop was `10.0.0.9`, interface `GigabitEthernet0/1`. Read the current entry, not a promised output.

**OSPF — B:**

> OSPF is a link-state routing protocol that uses cost to select paths. With the same failed direct link, the current route shows [actual next hop/interface] and ping shows [actual outcome]. Together these establish whether traffic can reach the destination through R3.

Again show `show ip route`; `O` identifies an OSPF route. The previously verified alternate next hop/interface was `10.0.0.9` / `GigabitEthernet0/1`. Show the path R1 → R3 → R2 on the topology. If a startup CLI dialog appears, answer `no` and wait for the prompt before `enable`.

**B — after restoring the interface:**

> These observations demonstrate reachability and alternate-route selection in the simulator. We are not claiming an exact convergence time or that one protocol is faster based on a few pings. Initial ARP or routing convergence can temporarily lose replies; we retain those observations.

Use simulation event/path views if rehearsed, but routing-table entries plus ping are the core evidence. If Fast Forward Time is used, describe it as advancing simulated time; do not report wall-clock convergence speed from it.

## Questions to prepare for

| Question | Direct answer |
| --- | --- |
| Is it hardcoded? | The payload and preset settings are predefined. The proxy really delays/paces/closes HTTP connections; measurements come from requests. Packet Tracer is the simulated component. |
| Why use a proxy? | It provides a controlled interception point while keeping dashboard control traffic separate. |
| What do availability, median and p95 mean? | Availability is successful non-cancelled requests divided by eligible requests. Median is the middle successful timing; p95 is nearest-rank 95th percentile. Three samples are descriptive, not a statistical reliability claim. |
| Is throughput the Wi-Fi speed? | No; it is complete-request payload goodput for successful responses. |
| Why two dashboards? | Saved automated comparisons versus manual live forwarding/configuration/monitoring. |
| Are Packet Tracer and FaultNet integrated? | No. They demonstrate related resilience concepts through separate evidence. |
| Is connection interruption packet-loss injection? | It closes an HTTP/TCP connection; it does not configure an IP packet-drop rate. |
| Does FaultNet repair failures? | It clears its own injected fault and observes responses. Routing failover belongs to the separate Packet Tracer test. |
| Where are results? | Local results/ JSON records persist. Live configuration/monitor are memory-only. Captures are local files; neither records nor captures transfer through source pushes. |
| Did we prove OSPF is faster than RIP? | No. We demonstrated reachability/path changes, not measured comparative convergence time. |

## Recovery if the presentation goes wrong

Read the observed result instead of the expected result. If a tool fails, use labelled prior evidence and continue explaining its settings and limits. For blocked Start, check readiness, active run and combined budget. For an empty capture, check same-laptop loopback/filter/capture start. For ping failures, confirm file, addresses, failed interface and routing convergence; restore the link. Do not manufacture success or bypass a browser security warning.
