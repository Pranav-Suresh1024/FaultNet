# FaultNet live proxy design

The user's 13 October request authorizes closer functional and visual parity with the demonstrated live proxy cockpit. Implement independently written FaultNet code on the existing application branch. Keep the experiment workbench and schema-v1 records; do not touch the teammate's lab branch or rewrite Git history.

## Behavior

- A fourth loopback listener, port 8080, routes real HTTP requests. The control UI remains on 3000; demo and experiment proxy remain on 3001/3002. Startup defaults the live target to the synthetic demo with every fault disabled.
- A dark monospace, amber-accented three-column cockpit becomes the landing page. `/workbench` retains the existing experiment dashboard. Columns contain setup/presets/header controls; network/failure/status/mock controls; and live traffic statistics/monitor.
- Unified mode uses one HTTP/HTTPS development target. Split mode uses frontend/backend targets and comma-separated backend path prefixes. Targets must be absolute origin URLs without credentials, paths, queries or fragments. Reject this application's control/proxy listener ports on loopback and metadata/unspecified/multicast targets, including DNS answers; resolve once per upstream request. No public listeners, CONNECT, WebSockets, production use or TLS interception.
- Request/response delay: integer 0–5000 ms each. Jitter: integer 0–1000 ms, independently adds a uniform signed variation to each direction's delay, clamped to zero. Upload/download body limits: integer 0–500000 KiB/s, with zero unlimited. Stream in bounded chunks, honor backpressure, and cancel timers/sockets. Presets: clear, Fast 4G, Slow 4G, 3G and EDGE.
- Failure modes: normal; 60-second wait before response; send headers then stall body until cancellation/deadline; send a partial body then disconnect. Failure modes apply deterministically per eligible response. Every request has a 120-second ceiling. Reset clears all faults/rules and cancels in-flight work while retaining targets; Apply affects subsequent requests.
- Up to eight status rules: path prefix, status 400–599, probability 0–100%. First matching successful probability check wins. Then first active matching mock rule returns status 200 with operator-supplied valid JSON (up to 1024 UTF-8 bytes per rule). Otherwise stream upstream. At most eight mocks. Mock/status responses also receive response delay/bandwidth/header/failure effects. HEAD and no-body statuses obey HTTP semantics.
- Header controls strip CORS headers, strip cache headers, or replace Content-Type with a deliberately mismatched type. Do not add permissive CORS after stripping it.
- Monitor retains the latest 50 completed requests in memory: generated ID, method, pathname only, status, elapsed milliseconds, transferred bytes, outcome and applied fault labels. Never retain query strings, bodies, cookies, authorization, targets or tokens. Summary cards and a duration visualization describe this window, not all-time data. Clear monitor removes only memory entries.
- Capability-protected `/api/live/config`, `/api/live/activity`, `/api/live/reset`, `/api/live/probe` and `/api/live/activity/clear` reuse existing Host/Origin/JSON/rate/body protections. A five-second sample GET reports outcome/status/bytes/time, without returning the body. Use only the local demo in automated/browser checks.
- Changes remain drafts until Apply; show validation/offline/unsaved states. Reload reads applied configuration. Live config/monitor reset when Node restarts; experiment results remain on disk. Accessible labels, keyboard-operable controls and responsive reflow are required.
